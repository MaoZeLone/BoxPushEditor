# 修改记录

完成一轮会留下的文件改动后，立刻写入 **当天** 的按日文档。不要等用户提醒。不要把记录写进回复里代替写文件。

路径：`文档/修改记录/YYYY-MM-DD.md`（日期用会话里的 Today）。

## 何时记

记：本轮结束时磁盘上仍在的代码、资源、设计文档改动（含新建、删除、重命名）。

不记：

- 只读、搜索、试跑、对话，没有改文件
- 改完又全部撤回，最终无净变化
- 只改了 `文档/修改记录/` 下的按日文档或目录索引
- 用户明确说这次不用记

同一条用户请求里的相关改动合并成 **一条**。不要每个文件一条。

## 怎么写

1. 先做完功能改动，再写记录（记录要描述最终结果，不是过程）。
2. 当天文件不存在就新建，并在 `文档/修改记录/README.md` 链接列表 **最上方** 加一行。
3. 条目插在当天文件标题下方、已有条目之上（当天内最新在上）。
4. 三个字段都必须有实质内容，禁止空话。

当天文件模板（仅新建时用）：

```markdown
# 修改记录 · YYYY-MM-DD

最新在上。

---
```

条目模板：

```markdown
## 不超过 20 字的标题

- **修改的内容：** 具体改了什么（文件/系统/行为）。点名关键路径或类型名。
- **为什么修改：** 针对什么问题、需求或阻塞。
- **好处是什么：** 改完之后谁更好用、哪条路径更稳、少了什么坑。
- **涉及文件：** `path/a`、`path/b`
```

目录索引新增一行（仅新的一天）：

```markdown
- [YYYY-MM-DD](YYYY-MM-DD.md)
```

## 写法

- 写结果，不写过程（不要「先搜再改」「用了某某工具」）。
- 「修改的内容」用事实：加了什么、删了什么、行为从 A 变成 B。
- 「为什么修改」写原因，不重复「修改的内容」。
- 「好处是什么」写可感知收益（可玩、可配、少崩溃、好接下一阶段），不要「代码更优雅」这种空句。
- 三个字段各 1～3 句。标题像 commit subject。日期只出现在文件名和文首，不要写进每条标题。
- 不要贴大段 diff。不要写密钥、账号、本机绝对路径。

## 反例

- 修改的内容：优化了代码
- 为什么修改：为了更好
- 好处是什么：提升了质量
